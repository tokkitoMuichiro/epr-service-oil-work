# ERP АММИР — контекст проекта

Живой бриф продукта. Обновлять при изменении статуса модулей.

## Цель

Внутренняя ERP для компании АММИР: контракты и графики объектов, персонал и бригады с контролем обучения, ежедневные полевые отчёты, учёт оборудования. Заменяет разрозненные инструменты эпохи Битрикс. Только русский UI и доменные термины; без расширения скоупа за пределы этих модулей.

## Стек (не менять без решения)

- Клиент: Vite + Vue 3 + TypeScript + Pinia + Vue Router, FSD. Без Nuxt и сторонних UI-библиотек.
- Сервер: Express 5 + TypeScript, модули в `server/src/modules/*`. Хранение — SQLite через встроенный `node:sqlite` (`server/src/db.ts`): состояние модуля — JSON-снимок в таблице `snapshots`, файлы — BLOB в `files`, плюс `users`, `sessions`, `audit_log`. Репозитории работают со снимком в памяти и сохраняют его после каждой мутации (`persisted`). Сиды пишутся только в пустую базу.
- Авторизация: логин/пароль (scrypt), httpOnly cookie-сессия; роль — из сессии, не из заголовка. В dev — демо-пользователи `demo.<роль>` и переключатель ролей (`/api/auth/dev-login`).
- Общий слой: `shared/src` — типы и чистая логика (права, валидация, даты), используется клиентом и сервером.
- Тесты: `node:test` через `tsx`; `npm run check` перед сдачей.
- Хостинг: VDS, один процесс Node (API + SPA) за nginx — см. `docs/deploy.md`.
- Дизайн: бренд модуля учёта оборудования — Montserrat, midnight `#242d3d`, dodger `#0088ff`, radius 2px. Светлая и тёмная темы на семантических токенах. Подробности — раздел «Дизайн-система».

## Дизайн-система

Все токены — в `client/src/app/styles/index.css`, в три слоя:

1. **Примитивы палитры** (`--midnight`, `--dodger`, `--ok`, `--warn-bg`…) — только внутри `index.css`, в компонентах запрещены.
2. **Семантические токены** — единственное, что используют компоненты:
   - поверхности `--surface-{app,card,raised,sunken,inverse,overlay}`, текст `--text-{primary,secondary,disabled,link,on-accent,on-inverse…}`, границы `--border-{subtle,strong,inverse…}`;
   - акцент `--accent`, `--accent-strong` (заливка основной кнопки, контраст AA), `--accent-subtle`, `--focus-ring`;
   - статусы `--status-{ok,warn,bad,info,neutral}-{fg,bg,border,solid}`; таблица `--table-head-bg`, `--row-hover-bg`, `--row-selected-bg`; график `--chart-*`; тени `--shadow-{card,raised,modal}`.
3. **Шкалы**: шрифт `--font-size-{2xs 11,xs 12,sm 13,base 14,md 16,lg 18,xl 22,2xl 28}` и `--page-title-size` (28 → 22 на ≤ 860px), отступы `--space-1…10`, `--control-height` 44 / `--control-height-sm` 40, `--tap-size` 44, `--z-*`, `--safe-*` (safe-area).

Брейкпоинты: 560 (телефон), 860 (планшет / мобильная оболочка), 1280 (полный сайдбар). На ≤ 860 поля ввода 16px (без зума в iOS), hover-стили — только внутри `@media (hover: hover) and (pointer: fine)`. Поддержаны `prefers-reduced-motion` и `forced-colors`.

Общие классы: `.ui-badge--{ok,warn,bad,info,neutral}`, `.ui-table` / `.ui-table-wrap` (тени прокрутки), `.ui-segmented`, `.ui-overline`, `.ui-form*`, `.ui-control`, `.ui-overlay` / `.ui-sheet` (на ≤ 560 — полноэкранный лист), `.ui-icon-button`, `.ui-skeleton`. Компоненты `shared/ui`: `UiButton` (`size="icon"`), `UiDialog` (слот `footer`, Esc, блокировка прокрутки, фокус), `UiState` (`kind="loading|error|empty"`), иконки `shared/ui/icons`.

Иконки — inline SVG по мотивам [Lucide](https://lucide.dev) (лицензия ISC), сетка 24, обводка 1.75; пакет не подключается. Шрифт Montserrat (OFL) хранится локально в `client/public/fonts` (кириллица и латиница, variable 100–900), Google Fonts не используется. PWA: PNG-иконки 192/512, `apple-touch-icon` 180, `black-translucent` статус-бар; цель сборки — `baseline-widely-available` (iOS Safari 16.4+).

Темы: светлая, тёмная и системная (по `prefers-color-scheme`). Тёмная тема переопределяет только семантические токены в `:root[data-theme='dark']` внутри `@media screen`, поэтому печать всегда светлая. Роли акцента: `--accent` — индикаторы (активная полоса, фокус, рамки выбора), `--accent-strong` — заливка под белым текстом, `--brand-mark-bg` — фирменный знак в обеих темах, `--danger-solid` — заливка кнопки удаления, `--border-inverse-edge` — контур тёмных плашек (прозрачный в светлой теме). Предпочтение хранится в `localStorage` `erp-theme` (`shared/lib/theme.ts`, ключ совпадает с inline-скриптом в `client/index.html`, который ставит `data-theme` до загрузки стилей). Переключатель — `features/theme-switch` (`ThemeSwitch`, `useTheme`): в футере сайдбара и мобильного меню — три сегмента, в rail — одна кнопка, циклически меняющая режим. Вкладки синхронизируются через событие `storage`, `meta theme-color` совпадает с `--surface-inverse`.

Оболочка: ≥ 1280 — сайдбар 264px; 861–1279 — свёрнутый rail 72px (состояние в `localStorage` `erp-sidebar-collapsed`); ≤ 860 — шапка 56px, выезжающее меню и нижняя таб-панель.

## Продуктовые правила

1. Контракты вводятся вручную (не из Битрикс): название, заказчик, год, объекты (например, резервуар на НПС), сроки план/факт, работы.
2. График линейный: список контрактов слева, объекты разворачиваются, горизонтальная шкала. Отставание / досрочно, отметки правки сроков. Зависимостей задач нет.
3. Объекты ежедневных отчётов = объекты контрактов, не задачи Битрикс.
4. Bitrix Disk (папка «учет персонала», `.txt` отчётов, Excel оборудования) — мок до реальной интеграции.
5. Бригады: бригадир — назначение; один человек не состоит в двух бригадах; статусы работает / свободен / запланирован; планирование — диапазоны дат на объектах без пересечений для одной бригады.
6. ПДн (СНИЛС, паспорт, дата рождения) видит и редактирует только Администратор; фильтрация на сервере.
7. Роли: Администратор / Офис / Мастер / Кладовщик / Инженер ОТ (обучение: каталог, тесты, назначения, результаты). Одна матрица прав на всю систему (`shared/src/access.ts`), редактируется в модуле «Настройки»:
   - Администратор — всё, его столбец не редактируется; права «ПДн» и «Управлять правами» выдаются только ему.
   - Офис — просмотр всех блоков (в оборудовании — «Видеть всё»), без редактирования.
   - Мастер, Кладовщик — просмотр контрактов, персонала, отчётов; в оборудовании — матрица `ROLE_PERMISSIONS` из исходного модуля.
   - Проверка — на сервере: чтение блока требует права просмотра, изменение — права редактирования.
8. Допуски (`shared/src/qualifications.ts`): справочник видов (ОТ, ЭБ, ПожБ, Высота, ГОР, ЗП, ПП, СИЗОД, Медосмотр, ПБ) со сроками по умолчанию; документ сотрудника может быть допуском (вид, номер, дата выдачи, кем выдан, группа), иначе — «Прочее». Матрица «должность → обязательные допуски» правится в «Настройках» (право `settings_manage`). Отсутствующий обязательный допуск = просрочен.
9. Назначение бригады проверяет допуски всех сотрудников (по должности + требования объекта; по умолчанию у объекта — набор для зачистки резервуаров: ГОР, ЗП, ОТ, СИЗОД, медосмотр) на весь период. Нарушение — 409 с перечнем «сотрудник — допуск — дата». Назначить вопреки может роль с правом `brigades_override` с обоснованием (≥ 10 символов), запись идёт в журнал `audit_log`. Выход за плановые даты объекта — предупреждение, не блок.
10. Уволенные не попадают в состав бригады и отчёта; отпускники помечены и не подставляются в отчёт. Увольнение выводит из бригады и предупреждает об оборудовании, числящемся за сотрудником.
11. Удаление с историей запрещено: сотрудника с документами/назначениями — только увольнение; бригаду, объект, договор с отчётами или прошлыми назначениями — только архив (409). Архив и удаление снимают лишь будущие назначения; в архивную бригаду/объект назначать нельзя.
12. Оборудование повторяет [-quipment-accounting](https://github.com/tokkitoMuichiro/-quipment-accounting): категории оборудование / транспорт (госномер, уникален) / карты (без состояния и документов, не уходят в ремонт); передача сотруднику или на базу ждёт принятия, на базу «Ремонт» — сразу; «Требует ремонта» / «В ремонте» / «Не подлежит ремонту» требуют пояснения; замечание по заполнению блокирует передачу до подтверждения ролью с правом «Проверять заполнение».
13. Обучение (`shared/src/training.ts`): программы не привязаны к должностям — администратор или инженер ОТ сам назначает любую программу сотруднику любой должности; в карточке и сводке видны только назначенные программы. Статусы: «Сдана», «Истекает», «Просрочена», «Не сдана», «Назначена» (активное назначение важнее результата); сотрудник без обучений — «Не назначена». Обучение и допуски независимы: «Допуски по должности» и проверка бригад учитывают только документы сотрудника, результаты тестов в допуски не засчитываются. Внеочередная проверка заменяет активное очередное назначение; не сданная внеочередная делает программу проблемной до пересдачи. Увольнение отзывает активные назначения. Публичная страница не отдаёт телефон и правильные ответы; сервер проверяет таймер и число попыток.

## Открытые вопросы

- Реальная интеграция с Битрикс (Disk, выгрузки, SSO).
- Просмотр журнала действий (`audit_log`) в интерфейсе; привязка пользователя к карточке сотрудника (`workerId`) пока не редактируется в UI.
- nginx `client_max_body_size 2m` меньше лимита документов (20 МБ).
- P1–P2 из `docs/business-analysis.md`.
- Линтер не настроен (новые зависимости — только по согласованию).
